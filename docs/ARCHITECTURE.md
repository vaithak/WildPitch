## Tick order (sim_step)
`events = 0` → `players_step` (per player: buttons → kicks, movement/turn, contact on the wind-up tick, jump/
timers; then ball control/dribble for human-controlled players) → `ball_step` (substeps of ≤ 8 cm: forces →
integrate → bounce/roll → posts/crossbar → bodies → goal line/touchline/net) → `match_flow` (goal/out pauses,
kickoff reset) → `prev_buttons`, `tick++`.
**Events** (`SimState.events`, WP_EV_*) are raised during the tick; presentation ORs them over a frame.
`WP_EV_RESET` means teleport: main.c sets `prev = cur` and resets avatar animation (no interpolation).

## Data flow
```
SDL events/keyboard/gamepad ──► WpInput (per seat: stick int8 x/y + button bits) ──► sim_step()  60 Hz
                                                                                         │
                                     render(prev, cur, alpha) ◄── SimState snapshots ◄───┘
```
- **Fixed step:** `main.c` accumulates real time and calls `sim_step` at exactly 60 Hz; rendering interpolates
  between the previous and current `SimState` with `alpha`. After a stall (>250 ms, e.g. lid closed) the
  accumulator is clamped so the game resumes instead of fast-forwarding.
- **Inputs are the only way in.** That makes replays (store `WpInput` per tick), lockstep netcode (exchange
  `WpInput`), and headless training (synthesise `WpInput` / AI decisions) the same mechanism.

## Determinism
- `fx` = int32 Q16.16; products via int64. Sim compiled with `-fwrapv`. Arithmetic right shift assumed (gcc/clang).
- `sim_hash()` hashes fields explicitly (not raw bytes), so struct padding can't cause false mismatches.
- `tests/test_determinism.c` checks: two runs equal; snapshot (struct copy) + resume equals straight run;
  final hash equals the golden file. `tools/check_determinism.sh` repeats under gcc/clang × -O0/-O2.
- Order matters: iterate players by index, never by pointer address or hash-map order.

## Rendering (D-006)
SDL_Renderer + `SDL_RenderGeometry` for filled shapes. `wp_project(cam, x, y, z)` maps world metres to screen:
depth (y) is foreshortened by `tilt` and scaled by a mild perspective factor; height (z) lifts straight up.
Sprites are depth-sorted by y (far first). Ball height reads via its ground shadow shrinking/fading.

## Avatars (D-009)
`wp_avatar_draw(pose, look, style)` is independent of SimState; `render.c` fills `WpAvatarPose` from the sim
(facing smoothed + stride phase from `WpAvatarAnim`, action + action_timer, jump z). Pose solver: per-joint angles
(`build_pose`) → 17 joint positions (`solve`), lowest foot snapped to the grass (+ jump z) which yields natural
running bob → parts (kit-coloured capsule segments) sorted along the camera depth `y - tilt*z` → silhouette outline
pass, then fills; limbs in front of the body get their own outline. Antialiasing comes from one 64×64 soft-disc
texture (linear filtered) used for every disc and capsule. Add a new action = add a case in `build_pose`.
Aerial stances (D-052): `WpAvatarPose.stance` / `stance_t` / `stance_tgt` (the ball's centre at the contact, in his
frame) come from `stance_vis.c`; the avatar fits the stance's few free parameters (a coordinate search over `solve`,
preferring the limb to a lunge) every frame the stance shows, so the limb is on the ball at stance_t = 0.

## Kick pipeline (D-012)
Input (or AI/tests via `sim_player_kick`) → `WpKick{power, vz, spin, dir, foot, kind, windup}` → action KICK;
contact on tick `windup` (owner's ball gathered to the foot during wind-up) → ball velocity = dir·power +
0.5·kicker velocity. The avatar reads the same `foot/kind/windup` so the strike lands on the contact tick;
`wildpitch --check-kick-pose` (also a ctest) asserts the instep is at the ball on that tick for every kind/foot.

## Performance notes
- Avatars: 10 animated players, 60 fps: ~5% of one core (dev desktop, `--demo`, both styles).
- CP0.1 full game loop (`--autoplay`): ~5% of one core. `bench_sim`: ~22,700× real time (0.73 µs/tick).
- `bench_sim` (CP0.0, dev desktop): ~2.3 M ticks/s (~38,000× real time) for the AI-less 5v5 skeleton.
  Meaningless for training headroom until AI exists; keep ≥ 500× real time for Phase 1 training.
- Frame loop sleeps in vsync; the deadline pacer (pacer.c) caps it when vsync is missing or ignored. Battery mode
  = 30 fps. Measurements: docs/PERF.md.
