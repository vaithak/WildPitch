## Q1. Which open-source football games have readable source for the controlled player's approach to the ball, and how does each handle it overall?

### Takeaway
Three projects with real, substantial source cover the whole range: **SWOS** (pure 8-way input for the selected man, but a *second, CPU-driven teammate* automatically chases loose balls/passes and takes control on arrival; the selected man auto-switches to whoever is nearest), **YSoccer** (pure input for the selected man, stops when the stick is neutral; all assistance is in the *auto-switch*, which uses a ball-trajectory "frames to reach" prediction), and **GRF** (an explicit, tunable **"magnet"** that blends stick input with an AI "get to the ball" interception vector, on by default). Other names in the brief (Bygfoot = management only; Tux Football, OpenSoccer, Kick Off clones) were not investigated in code — see Gaps.

### Cited Findings
- SWOS port contains both a C++ re-implementation of player updates (`src/game/updatePlayers/*.cpp`, `src/game/player.cpp`, `src/game/ai/ai.cpp`) and the annotated original disassembly (`swos/swos.asm`), where the controlled-player selection routines (`UpdateControlledPlayer`, `UpdatePlayerBeingPassedTo`) still live — [SWOS repo](https://github.com/zlatkok/swos-port)
- YSoccer's Java port (from BlitzMax) is in the SourceForge git repo, `java/` with a Gradle `desktop:run` task — [YSoccer forum post](https://ysoccer.sourceforge.io/ysf/viewtopic.php?p=3851); [SourceForge project](https://sourceforge.net/projects/ysoccer/)
- GRF's `ScenarioConfig` has `bool use_magnet = true;` with comment "Whether to use magnet logic (that automatically pushes active player towards the ball)" — [GRF src/main.hpp](https://github.com/google-research/football/blob/master/third_party/gfootball_engine/src/main.hpp) (exposed to Python in `third_party/gfootball_engine/ai.cpp` as `use_magnet`)

### Inferences
- The three designs form a spectrum useful for WildPitch: (a) no steering of the human's man + aggressive auto-switch (YSoccer), (b) no steering of the human's man + an AI teammate that runs to the ball and is handed control (SWOS), (c) direct steering blend on the human's man (GRF magnet).

### Gaps
- Did not inspect code for Tux Football, OpenSoccer, Kick Off clones, "FreeKick", "Ultimate Soccer", "Yorg" — limited tool budget; prioritised the three projects with the most relevant, maintained source.

## Q2. SWOS (swos-port): selected-player control, ball-control radius, auto-run when joystick released, auto-switch

### Takeaway
In SWOS the **human-selected player never moves toward the ball on his own**: with no direction pressed his destination is set to his own position (he stops), and with a direction pressed he moves exactly one 8-way step. Assistance comes from (1) **auto-switching control to the closest player (squared pixel distance) to the ball**, recomputed each frame (teams alternate frames), and (2) a separate **"pass receiver"** teammate (`passToPlayerPtr`) that is *CPU-driven* toward the ball's current position (pure pursuit, no interception prediction for outfielders) and **becomes the controlled player once he's within the control radius**, followed by a 25-tick switch cooldown.

### Cited Findings
- **Neutral stick = stop.** `updateControlledPlayer()` calls `stopPlayer(player)` (destX/destY := current x/y) when `!hasDirection(team.currentAllowedDirection)`; movement only via `setControlledPlayerDestination()`, which sets the destination to position + `getDefaultBallDestinations()[directionIndex]` for the 8-way direction (blocked at pitch boundary + 2 px margin) — [SWOS src/game/updatePlayers/updateAllPlayers.cpp](https://github.com/zlatkok/swos-port/blob/master/src/game/updatePlayers/updateAllPlayers.cpp)
- **No cone / angle tolerance between stick and ball for the human's runner**; the only "ball control" gating is distance bands. `classifyBallForPlayer()` (squared distances): `plVeryCloseToBall` if `ballDistance <= 32` (≈5.7 px), `plCloseToBall` if `<= 72` (≈8.5 px), `plNotFarFromBall` if `<= 2450` (≈49.5 px); ball height bands ≤4, 4–8, 8–12, 12–17, >17 — [SWOS src/game/updatePlayers/playerUpdateCore.cpp](https://github.com/zlatkok/swos-port/blob/master/src/game/updatePlayers/playerUpdateCore.cpp)
- `ballDistance` is the **squared** distance: disassembly comment "D1 = sqr(player x - ball x) + sqr(player y - ball y)" then "update player's distance from the ball" in `UpdateControlledPlayer` — [SWOS swos/swos.asm](https://github.com/zlatkok/swos-port/blob/master/swos/swos.asm)
- Dribble/ball pickup by the selected man happens when `plVeryCloseToBall && !ballAbove17 && !ball12To17` (i.e., ball ≤12 high) — he "controls" the ball by just walking into it — [SWOS updateAllPlayers.cpp](https://github.com/zlatkok/swos-port/blob/master/src/game/updatePlayers/updateAllPlayers.cpp)
- **Auto-switch to nearest:** asm header for `UpdateControlledPlayer`: "Update players distance from the ball. Update controlling player if he's closest to the ball. Stop him if he was getting passed to." The loop picks the closest player excluding goalkeeper, the current pass receiver, and players in tackling/tackled/jump-heading/static-heading/injured states; the *old* controlled player, if in normal state, is stopped (dest := position). Gated by a team flag `ballOutOfPlay` that the C++ code sets to true when a kick is made and clears in `stopAllPlayers()` — [SWOS swos/swos.asm](https://github.com/zlatkok/swos-port/blob/master/swos/swos.asm); [SWOS src/game/team.cpp](https://github.com/zlatkok/swos-port/blob/master/src/game/team.cpp)
- `UpdateAndApplyTeamControls` (called once per frame) "Handles one team per frame (next team in next frame)" and calls `UpdateControlledPlayer` then `UpdatePlayerBeingPassedTo` before reading the joystick — [SWOS swos/swos.asm](https://github.com/zlatkok/swos-port/blob/master/swos/swos.asm)
- **Second-nearest teammate auto-chases:** `UpdatePlayerBeingPassedTo` (asm comment: "Find closest player being passed to and update passToPlayerPtr. Stop him so he can get the pass if game is running") copies the ball's current x/y into `team.ballX/ballY` every frame; if ball in play, `playerSwitchTimer == 0`, and no precise pass already has a receiver, it picks the closest *non-controlled* outfield player in normal state as `passToPlayerPtr` — [SWOS swos/swos.asm](https://github.com/zlatkok/swos-port/blob/master/swos/swos.asm)
- That receiver is updated via `updatePassReceiver()` → `setPlayerBallChaseDestination()`: constant `kNearbyBallDistance = 3'200` (squared, ≈56.6 px). If no pass is in flight and the controlled player is within 3200 *and* at least as close as the candidate, the candidate holds still; otherwise `team.passingBall = true` and `player.destX/destY = team.ballX/ballY` (the ball's **current** position — pure pursuit) — [SWOS playerUpdateCore.cpp](https://github.com/zlatkok/swos-port/blob/master/src/game/updatePlayers/playerUpdateCore.cpp)
- **Hand-over on arrival:** `passReceiverCanControlBall()`: ball height ≤4 and (`ball.speed >= 3.0` px/tick and `plCloseToBall`) or `plVeryCloseToBall` — i.e., fast passes are caught from the wider ≈8.5 px radius, slow ones need ≈5.7 px. Then `passReceiverTakesControl()` sets `team.controlledPlayer = team.passToPlayerPtr`, `playerSwitchTimer = kPlayerSwitchCooldown` (25, defined in `updatePlayers.cpp`) and stops the player — [SWOS playerUpdateCore.cpp](https://github.com/zlatkok/swos-port/blob/master/src/game/updatePlayers/playerUpdateCore.cpp); [SWOS updatePlayers.cpp](https://github.com/zlatkok/swos-port/blob/master/src/game/updatePlayers/updatePlayers.cpp)
- **Pass receiver choice uses a facing cone:** `doPass()` → `getClosestNonControlledPlayerInDirection()`: among non-controlled, not-sent-off, normal-state players whose `fullDirection` (256-unit circle) is within ±16 (±22.5°) of `direction*32`, pick the smallest `ballDistance` — [SWOS src/game/player.cpp](https://github.com/zlatkok/swos-port/blob/master/src/game/player.cpp)
- **Human "lead" assist for aftertouched passes:** `updateHumanPassAssistTarget()` (comment: "Lead a human-controlled pass receiver according to the ball's approach angle and the aftertouch applied to the pass") — only for human teams, when long pass / spin aftertouch was applied and ball speed ≥1.0: angle difference between ball direction and receiver direction (uint8, 256 = 360°) in (64,192) cancels the pass chase; ≤4 or ≥252 sets target = receiver's own position (wait there); otherwise a lead angle of ±32 (long pass) or ±64 is added and an offset from the 32-entry `kPassAssistOffsets` table (components ±1000/668/414/199/0) is added to the receiver position as the chase target — [SWOS playerUpdateCore.cpp](https://github.com/zlatkok/swos-port/blob/master/src/game/updatePlayers/playerUpdateCore.cpp); [SWOS updatePlayers.cpp](https://github.com/zlatkok/swos-port/blob/master/src/game/updatePlayers/updatePlayers.cpp)
- **Ball prediction exists only for goalkeepers:** `updateGoalkeeperBallProjections()` and `calculateBallNextGroundXYPositions()` simulate the ball tick by tick (air friction on z) to find goal-line crossings / landing points; comment says "Goalkeeper logic uses this point to decide whether to intercept, dive, or catch the ball" — [SWOS src/game/updatePlayers/ballProjections.cpp](https://github.com/zlatkok/swos-port/blob/master/src/game/updatePlayers/ballProjections.cpp)
- CPU-controlled teams produce the same virtual joystick signals as humans (`updateCpuPlayerControls()`), so "passing, shooting, tackling" share one implementation — [SWOS docs/cpu-ai.md](https://github.com/zlatkok/swos-port/blob/master/docs/cpu-ai.md)

### Inferences
- SWOS's feel ("the ball sticks to your feet; you are always the nearest man") comes from aggressive nearest-man switching + a generous pickup rule (walk into the ball within ~5.7 px, ball ≤12 high), not from steering. A released joystick genuinely stops the selected player.
- The "second runner" mechanism means a loose ball far from the selected man is still being chased by someone, and control transfers on arrival; this is effectively an "automatic go-to-ball" without touching the human's own player.
- The `ballOutOfPlay` name looks inverted relative to its use (set on kick, cleared on stoppage); I interpret it as "ball has been played since the restart". Not fully traced.

### Gaps
- I did not trace where `team.ballX/ballY` are overwritten for precise passes other than the human aftertouch assist; for ordinary passes they appear to equal the live ball position (inference from `UpdatePlayerBeingPassedTo`).
- No swos-port issue-tracker/forum discussion of "player doesn't go to the ball" was checked.

## Q3. YSoccer: is there a magnet, prediction, cone, or auto-run for the human player?

### Takeaway
No steering of the human's player at all: in `PlayerStateStandRun` speed is zero when the input device has no value, otherwise the player runs exactly at the stick angle. Assistance is (1) a **2-second ball-trajectory prediction** used to compute each player's "frames to reach the ball" (`frameDistance`), (2) **auto-switch** rules built on that, with hysteresis (switch only when the nearest is <0.5× the controlled player's frames-to-ball), and (3) AI teammates (including the pass recipient while still AI-controlled) running to the **predicted interception point**. Pass aim has a ±27.5° search cone with ±22.5° auto-correction.

### Cited Findings
- **Neutral stick = stop:** `if (player.inputDevice.value) { player.v = player.speed * (1 - 0.1f * (owner?1:0)); player.a = player.inputDevice.angle; } else { player.v = 0; }` — [YS PlayerStateStandRun.java](https://sourceforge.net/p/ysoccer/code/ci/master/tree/java/core/src/main/java/com/ygames/ysoccer/match/PlayerStateStandRun.java)
- **Ball control is a cone around facing, not steering:** if `ballDistance < 9`, control "slice" = `70 + 3 * skills.control` degrees (70°–91°); within slice and `ballDistance > 3.5` the ball is pushed with `ball.v = max(ball.v, m * player.v)`, `m = 1 + (0.06 - 0.004*control)`; ball angle snapped to player angle if diff ≤22.5°, else halved; outside the slice ball pushed at `1.2 * player.v` — [YS PlayerStateStandRun.java](https://sourceforge.net/p/ysoccer/code/ci/master/tree/java/core/src/main/java/com/ygames/ysoccer/match/PlayerStateStandRun.java)
- **Possession pickup ellipse:** `getPossession()` uses an ellipse with foci 6.5 px from the player at ±75° from facing, sum-of-distances < 14, ball z < `PLAYER_H` (22), and relative velocity `|playerVec - 0.5*ballVec| < 320 + 10*control` — [YS Player.java](https://sourceforge.net/p/ysoccer/code/ci/master/tree/java/core/src/main/java/com/ygames/ysoccer/match/Player.java)
- **Prediction horizon:** `BALL_PREDICTION = 2 * SECOND / GLGame.SUBFRAMES` with `SECOND = SUBFRAMES_PER_SECOND = VIRTUAL_REFRESH_RATE(64) * SUBFRAMES(8)` → 128 frames (2 s) — [YS Const.java](https://sourceforge.net/p/ysoccer/code/ci/master/tree/java/core/src/main/java/com/ygames/ysoccer/match/Const.java); `GLGame.java` in `framework/`
- **Frames-to-ball:** `updateFrameDistance()` scans predicted ball positions f = 127…0 and sets `frameDistance = f` for the smallest f with `dist(player, ball.prediction[f]) < speed * f / VIRTUAL_REFRESH_RATE` (also left/right-spin variants `predictionL/R`); unreachable = `BALL_PREDICTION` — [YS Player.java](https://sourceforge.net/p/ysoccer/code/ci/master/tree/java/core/src/main/java/com/ygames/ysoccer/match/Player.java)
- **Nearest player:** `Team.findNearest()` picks min `frameDistance` ("takes into account both the speed of the player and the speed and direction of the ball"), falling back to pixel `ballDistance` if nobody can reach within the horizon — [YS Team.java](https://sourceforge.net/p/ysoccer/code/ci/master/tree/java/core/src/main/java/com/ygames/ysoccer/match/Team.java)
- **Auto-switch rules** (`automaticInputDeviceSelection()`, called every update in `MatchStateMain` for teams using an automatic input device): own team owns ball → control the owner; opponent owns → `bestDefender` (closest to ball among players nearer own goal than 0.95× ball-to-goal distance, replaced only if <0.9× current best's distance) if `bestDefender.frameDistance < BALL_PREDICTION`; loose ball last touched by us → `near1` if `near1betterThan(controlled)`; loose ball last touched by opponent → bestDefender in own half, `near1` in opponent half — [YS Team.java](https://sourceforge.net/p/ysoccer/code/ci/master/tree/java/core/src/main/java/com/ygames/ysoccer/match/Team.java); [YS MatchStateMain.java](https://sourceforge.net/p/ysoccer/code/ci/master/tree/java/core/src/main/java/com/ygames/ysoccer/match/MatchStateMain.java)
- **Switch hysteresis:** `near1betterThan()` returns false if near1 is the goalkeeper, if the controlled player is not in STAND_RUN ("avoid stealing controls while still kicking"), or if near1 is the controlled player's `passingMate` ("passing mate, let him get the ball"); otherwise switch only if `near1.frameDistance < 0.5 * controlled.frameDistance` — [YS Team.java](https://sourceforge.net/p/ysoccer/code/ci/master/tree/java/core/src/main/java/com/ygames/ysoccer/match/Team.java)
- **AI ball-seeking aims at the interception point:** `AiStateSeeking.doActions()`: if `frameDistance < BALL_PREDICTION`, target `ball.prediction[frameDistance]`, direction `a = atan2(...)`, and the virtual stick is `(round(cos a), round(sin a))` (i.e., snapped to 8 directions); exits when no longer `team.near1` — [YS AiStateSeeking.java](https://sourceforge.net/p/ysoccer/code/ci/master/tree/java/core/src/main/java/com/ygames/ysoccer/match/AiStateSeeking.java)
- **Pass aim assist:** `searchPassingMate()`: `maxCorrectionAngle = 22.5`, `maxSearchAngle = 27.5`; among reachable mates (frameDistance < BALL_PREDICTION) in STAND_RUN/REACH_TARGET/IDLE, choose min frameDistance whose point 5 px ahead of them is within the search angle; applied in `PlayerStateKick` only when `angle_diff == 0`, adding `PASSING_SPEED_FACTOR * distance` to ball speed — [YS Player.java](https://sourceforge.net/p/ysoccer/code/ci/master/tree/java/core/src/main/java/com/ygames/ysoccer/match/Player.java); [YS PlayerStateKick.java](https://sourceforge.net/p/ysoccer/code/ci/master/tree/java/core/src/main/java/com/ygames/ysoccer/match/PlayerStateKick.java)
- Head/tackle on fire uses prediction: `ball.prediction[min(frameDistance, BALL_PREDICTION-1)]`, header if predicted z > 18, tackle if moving, ball in front, distance > 12 (and ball within 120 and approaching) — [YS PlayerStateStandRun.java](https://sourceforge.net/p/ysoccer/code/ci/master/tree/java/core/src/main/java/com/ygames/ysoccer/match/PlayerStateStandRun.java)

### Inferences
- Because the pass recipient (`passingMate`) is excluded from the switch rule until he owns the ball, he is still AI-controlled while the ball travels, so he runs to the predicted interception point via AiStateSeeking if he is `near1`; control jumps to him when `ball.owner` becomes him ("ball owner (attacking)" rule). Net effect: receiving a pass is fully automatic up to first touch.
- YSoccer's auto-switch uses *time-to-intercept* (trajectory-aware), not raw distance — a key difference from SWOS's squared-distance nearest-man.

### Gaps
- Did not examine the BlitzMax original or the `ysoccer-touch` variant for differences.

## Q4. Google Research Football: magnet, prediction, auto-switch, action set

### Takeaway
GRF has the most explicit assist: in `PlayerController::_MovementCommand` the human's stick vector is linearly blended with an AI "to-ball" movement vector by an `autoBias` weight (0…1). The to-ball vector comes from `AI_GetToBallMovement`, which searches the ball's predicted path (3 s horizon, 10 ms steps) for the best reachable interception point and also **re-quantizes the stick to 16 directions in "ball-direction space"**. The weight is 1 for the designated possession player / pressure button, and for others it scales with how well stick and auto direction agree (an implicit angle tolerance), recent touch, and time since switch; it is cancelled if the stick points toward your own half. Auto-switch selects the team's designated possession player when he can reach the ball 3× faster than the human's current player.

### Cited Findings
- Magnet on by default: `bool use_magnet = true;` ("automatically pushes active player towards the ball") — [GRF src/main.hpp](https://github.com/google-research/football/blob/master/third_party/gfootball_engine/src/main.hpp)
- **With magnet off**, `HumanController::RequestCommand` overwrites the movement command with raw input direction/velocity; if velocity < `idleDribbleSwitch` (1.8) the player faces `GetBallPrediction(500)` (ball 0.5 s ahead) and always looks at it — [GRF onthepitch/player/controller/humancontroller.cpp](https://github.com/google-research/football/blob/master/third_party/gfootball_engine/src/onthepitch/player/controller/humancontroller.cpp)
- **Blend formula:** `resultingMovement = manualMovement * (1 - autoBias) + autoMovement * autoBias;` velocity clamped to [idle, sprint]; if result velocity < idleDribbleSwitch the facing becomes `autoLookDirection` — [GRF onthepitch/player/controller/playercontroller.cpp](https://github.com/google-research/football/blob/master/third_party/gfootball_engine/src/onthepitch/player/controller/playercontroller.cpp)
- **When autoBias = 1:** if `forceMagnet` (pressure button held, or "actionMode == 2" i.e. a pass/shot is buffered) or the player is the match's designated possession player, or several team-possession conditions hold (`possessionAmount > 0.5` with recent touch, `> 0.99` "for air balls and such", or `hasBestPossession`). With possession → `AI_GetBallControlMovement`; without → `AI_GetToBallMovement` with `haste = 1` if extraHaste/forceMagnet — [GRF playercontroller.cpp](https://github.com/google-research/football/blob/master/third_party/gfootball_engine/src/onthepitch/player/controller/playercontroller.cpp); [GRF humancontroller.cpp](https://github.com/google-research/football/blob/master/third_party/gfootball_engine/src/onthepitch/player/controller/humancontroller.cpp)
- **Partial magnet (angle tolerance):** if not the designated possession player: `sameDirFactor = 1 - clamp(|angle(autoDirection, manualDirection)| / pi, 0, 1)`, remapped `*0.5 + 0.5`; if recently touched (`GetLastTouchBias(2000) > 0.01`) and time to ball < 1700 ms, `autoBias = lastTouchBias^0.4 * sameDirFactor^0.5`; if the opponent doesn't have possession and the player is externally (human) controlled, `magnetBias = max(curve(sameDirFactor, 0.8), lastSwitchBias^0.5)` (comment: "needed for when we get passed a ball while we are not the designated player. we want to at least try to get there."), multiplied by `(1 - inputDirIsOwnHalfFactor)` ("if we run for our own half, don't accidentally magnet somewhere"), and `autoBias = clamp(sqrt((max(possessionAmount,0.5)-0.5)*2) * magnetBias, autoBias, 1)` — [GRF playercontroller.cpp](https://github.com/google-research/football/blob/master/third_party/gfootball_engine/src/onthepitch/player/controller/playercontroller.cpp)
- **Defending:** when the opponent has the ball, the team's best player gets `autoBias = lastSwitchBias * 0.3` (only just after a switch), blending man-marking (within 7 m) and a "hunt" target in front of the opponent — [GRF playercontroller.cpp](https://github.com/google-research/football/blob/master/third_party/gfootball_engine/src/onthepitch/player/controller/playercontroller.cpp)
- **Switch smoothing:** `GetLastSwitchBias()` = 1 → 0 linearly over `lastSwitchTimeDuration_ms = 300` (human controller) after a switch; `_GetHidInput` blends current movement into input by `switchBias^0.7 * 0.5` so a newly selected player doesn't snap direction — [GRF playercontroller.cpp](https://github.com/google-research/football/blob/master/third_party/gfootball_engine/src/onthepitch/player/controller/playercontroller.cpp); [GRF humancontroller.cpp](https://github.com/google-research/football/blob/master/third_party/gfootball_engine/src/onthepitch/player/controller/humancontroller.cpp)
- **Neutral stick:** below `analogStickDeadzone = 0.75`, input direction = current facing and velocity = `idleVelocity` (0) — so without magnet the player stops; with magnet the auto vector can still move him — [GRF humancontroller.cpp](https://github.com/google-research/football/blob/master/third_party/gfootball_engine/src/onthepitch/player/controller/humancontroller.cpp); constants in [GRF gamedefines.hpp](https://github.com/google-research/football/blob/master/third_party/gfootball_engine/src/gamedefines.hpp) (`dribbleVelocity 3.5`, `walkVelocity 5.0`, `sprintVelocity 8.0`, `idleDribbleSwitch 1.8`, `ballPredictionSize_ms 3000`, `ballDistanceOptimizeThreshold 10.0`)
- **Interception search (`AI_GetToBallMovement`)**: quantizes desired direction to 16 directions relative to the ball's travel direction ("quantize input 8- or 16-way in relation to 'ball direction space'"); iterates predicted ball positions from the player's time-to-ball up to 3000 ms in 10 ms steps (adaptive skip up to 100 ms), skipping points with z ≥ 1.0 m; for reachable points rates `movementRating` (0.4×velocity match + 0.6×direction match vs. stick) and `timeRating`; with haste weights become time-only (earliest reachable point). Forced early exit if `justInTimeFactor < 0.35` or if approaching from behind the ball (`dot > 0`, comment "too shallow angle, just go to ball already"); velocity = `clamp(timeNeeded/time * maxVelocity, idle, sprint)` — [GRF onthepitch/AIsupport/AIfunctions.cpp](https://github.com/google-research/football/blob/master/third_party/gfootball_engine/src/onthepitch/AIsupport/AIfunctions.cpp)
- **Time-to-ball** (`Player::UpdatePossessionStats`): scans ball prediction 0–3000 ms in 10 ms steps where predicted z < 1.5 m, using `AI_GetTimeNeededForDistance_ms`; default fallback uses distance to the 2990 ms prediction at 0.75× max velocity — [GRF onthepitch/player/player.cpp](https://github.com/google-research/football/blob/master/third_party/gfootball_engine/src/onthepitch/player/player.cpp)
- **Designated player hysteresis:** `timeRating = (bestTime+500)/(designatedTime+500)`, ×0.5 / ÷0.5 for possession, ×0.8 / ÷0.8 for human-controlled, +0.2 and ×1.2 if current designated beats the closest opponent by 100 ms; switch if `timeRating < 0.8` — [GRF onthepitch/team.cpp](https://github.com/google-research/football/blob/master/third_party/gfootball_engine/src/onthepitch/team.cpp)
- **Auto-switch:** `Team::UpdateSwitch()` "autoswitch on proximity": select designated player if not human-controlled, not GK, and `3 * designated.timeToBall < HumanControlledToBallDistance()` (min time-to-ball among human-selected players); also auto-select the teammate with unique possession — [GRF team.cpp](https://github.com/google-research/football/blob/master/third_party/gfootball_engine/src/onthepitch/team.cpp)
- **Manual switch** with stick direction: `AI_GetBestSwitchTargetPlayer()` chooses among players closest to an "action position" (mix of designated possession player and ball prediction 100 ms ahead, shifted defensive/offensive) — [GRF AIfunctions.cpp](https://github.com/google-research/football/blob/master/third_party/gfootball_engine/src/onthepitch/AIsupport/AIfunctions.cpp)
- **Agent action set:** 8 sticky directional actions, `action_release_direction` (reset movement), `action_idle` keeps sticky actions, and `action_builtin_ai` = 19 "let game's built-in AI generate an action" — [GRF gfootball/doc/observation.md](https://github.com/google-research/football/blob/master/gfootball/doc/observation.md)

### Inferences
- GRF's magnet is effectively "aim assist" for movement: full override for the clear ball-winner, and a cone-shaped partial assist (weight grows as stick aligns with the auto direction) for others; it deliberately avoids pulling a player who is running back toward his own half.
- The 300 ms post-switch blending plus `lastSwitchBias` term in magnet is specifically aimed at the "I was passed the ball but I'm not the designated player" case — matching the brief's "player doesn't go to the ball" problem.
- `enableSteadyDirectionSystem = false` with comment "just doesn't work so well … introduces too much lag" (in `HumanController::Process`) is a documented failed attempt at input smoothing.

### Gaps
